# 从需求到对象协作：真正重要的编程能力

> **软件框架与设计模式实践｜学生课堂讲义**  
> 贯穿案例：图书借阅

## 一、这节课真正要学什么？

学过 Java 语法之后，你可能已经能写类、创建对象、调用方法、实现接口。但是，面对一个稍微完整的功能，仍然容易卡住：

- 这个功能应该拆成哪些步骤？
- 哪个类负责哪一步？
- 对象之间由谁发起调用？
- 方法究竟需要什么参数、返回什么类型？
- 发生异常时，已经修改的对象怎么办？
- 类多起来之后，怎样判断设计是否合理？

**本课的核心观点：软件开发最重要的能力之一，是把一个真实问题转化为正确、可执行、可验证的程序，并组织多个对象完成这个任务。**

会写一个类，是基础；会让多个类各负其责、协同完成任务，才开始具备构造软件系统的能力。

这不意味着“类越多越好”，也不意味着必须套用设计模式。**最好的设计不是最复杂的设计，而是能够清楚表达需求、可靠运行，并且便于修改的设计。**

### 学完以后，你应该能做到

1. 从需求中整理出一条完整的**业务执行流程**。
2. 判断哪些规则应当由哪些对象负责，而不是随意分配方法。
3. 设计清晰的**方法契约**：参数、返回值、异常与状态变化。
4. 画出并解释一条真实的**对象调用链**，理解运行时的多态与对象状态。
5. 面对失败和需求变更，定位设计问题并作出有依据的调整。

## 二、从零开始：先想“做什么”，不要先想“建哪些类”

### 任务：实现借书

需求：用户借阅一本图书。只有处于正常状态的用户可以借书；图书必须还有可借库存。借书成功后，库存减少一本，并产生一条借阅记录。

**第一步：不要急着画类图，先把行为顺序写出来。**

```text
借书(userId, bookId)
  1. 找到用户
  2. 找到图书
  3. 检查用户资格
  4. 检查图书库存
  5. 减少可借库存
  6. 创建借阅记录
  7. 保存变更
  8. 返回借书结果
```

这叫**业务流程分解**。此时还没有做出完整的面向对象设计，但已经建立了程序执行的主线。

> **先有问题和行为，再逐步组织类。** 不要反过来，先画一堆类，再想这些类有什么事可做。

### 课堂练习 1（10 分钟）

不写 Java，先回答：

- 哪一步可能失败？失败原因是什么？
- 哪几步会修改数据或状态？
- 如果第 7 步保存失败，第 5 步减少的库存应该怎样处理？
- 借书成功后，调用者究竟需要知道什么结果？

这里没有唯一的实现方案，但每个方案都必须说清楚理由。

## 三、从流程到对象：把责任放到合适的地方

先看一种最直接的写法（省略查找和保存方法的实现）：

```java
public void borrow(long userId, long bookId) {
    User user = findUser(userId);
    Book book = findBook(bookId);

    if (!user.isActive()) {
        throw new IllegalStateException("用户不可借书");
    }
    if (book.getAvailableCopies() <= 0) {
        throw new IllegalStateException("图书无库存");
    }

    book.setAvailableCopies(book.getAvailableCopies() - 1);
    BorrowRecord record = new BorrowRecord(userId, bookId);
    saveBook(book);
    saveRecord(record);
}
```

这段程序的业务步骤很清楚，适合作为**第一版**。但请问：

**“用户是否有借书资格”的规则，必须写在 BorrowService 里吗？**  
**“库存不能减成负数”的规则，应该交给所有调用者重复检查吗？**

我们可以把这些规则放回真正掌握相关状态的对象中。

```java
// User：维护用户自身的资格规则
public void ensureEligible() {
    if (!active) {
        throw new IllegalStateException("用户不可借书");
    }
}

// Book：维护图书自身的库存规则
public void borrowOne() {
    if (availableCopies <= 0) {
        throw new IllegalStateException("图书无库存");
    }
    availableCopies--;
}
```

于是主流程变成：

```java
public BorrowRecord borrow(User user, Book book) {
    user.ensureEligible();
    book.borrowOne();
    return new BorrowRecord(user.getId(), book.getId());
}
```

现在出现了三种不同的职责：

| 类 | 应该负责什么 | 不必负责什么 |
|---|---|---|
| `User` | 自身资格和用户状态规则 | 整个借书流程、数据库存储 |
| `Book` | 自身库存及其约束 | 查询用户、组织整个借书流程 |
| `BorrowService` | 按顺序组织一次借书 | 亲自计算库存是否合法 |
| `BorrowRecord` | 表达一次借阅事实 | 决定全局借书流程 |

注意，这只是一种**合理的职责划分**，并非所有业务必须使用这些类。若系统很小，一个简单函数可能足够；只有当规则需要独立维护时，拆分类才更有价值。

### 课堂练习 2（10 分钟）

判断以下方法放在哪里更合适，并说明理由：

1. `ensureEligible()`：`User` 还是 `BorrowService`？
2. `borrowOne()`：`Book` 还是 `BorrowService`？
3. “用户最多同时借 5 本”：只靠 `User` 能判断吗？还需要哪些信息？
4. `sendBorrowSuccessNotice()`：应该放在 `Book` 里吗？

**关键判断：谁掌握完成这件事所必需的状态和规则？谁负责协调跨对象的工作？**

## 四、对象协作的关键：方法不是随便写的，它有契约

当你写出下面一行代码时：

```java
book.borrowOne();
```

你其实已经作出了四项设计决定：

| 契约问题 | 当前设计 |
|---|---|
| **谁做？** | `Book` 对象 |
| **给什么？** | 无参数：库存信息在 `Book` 内部 |
| **返回什么？** | `void`：目标是改变对象状态 |
| **失败怎么办？** | 库存不足时抛异常，库存不得被扣减 |

同样，看看三个常见方法：

```java
User findUser(long userId);                 // 输入 ID，返回 User
void ensureEligible();                     // 验证自身状态，失败抛异常
BorrowRecord borrow(User user, Book book); // 组织协作，返回借阅事实
```

### 设计方法签名的“五问”

每当一个对象需要请另一个对象帮忙，先问：

1. **谁负责？** 把方法放在哪个类中最自然？
2. **需要什么输入？** 已经在对象内部的信息，不必重复传入。
3. **返回什么？** 调用者真正需要一个值、一个对象，还是只需完成行为？
4. **会改变什么状态？** 哪个对象的哪个状态发生变化？
5. **失败如何表达？** 返回特定结果、抛异常，还是交由上层处理？

例如：

```java
book.borrowOne(book.getAvailableCopies()); // 通常是冗余输入
book.borrowOne();                          // 由 Book 自己管理库存
```

也不要为了“显得面向对象”，把简单值都包装成大量一次性的类。参数和返回值应当**表达清楚业务意义，同时保持必要的简单**。

### 补充：Java 对象参数究竟传的是什么？

```java
void use(Book book) {
    book.borrowOne();
}
```

Java **始终按值传递参数**。这里传入的是“对象引用的值”，方法内的 `book` 与调用者的变量可以指向同一个 `Book` 对象。因此 `book.borrowOne()` 能改变这个对象的内部状态；但给形参 `book` 重新赋值，不会改变调用者变量所保存的引用。

## 五、从类图走向执行：画一条能够运行的调用链

对象多了以后，最容易迷失在“你调我、我调你”的关系中。解决办法不是把所有类背下来，而是**沿一条完整业务场景追踪协作**。

```text
调用者
  │ borrow(user, book)
  ▼
BorrowService
  ├── user.ensureEligible()   → User：资格检查
  ├── book.borrowOne()        → Book：扣减库存
  └── new BorrowRecord(...)   → 创建借阅记录
  │
  └── 返回 BorrowRecord
```

看一条调用时，请刻意区分四件事：

| 要观察的关系 | 问题 |
|---|---|
| **对象关系** | 哪个对象持有哪个对象的引用？ |
| **调用关系** | 此刻是谁调用了谁的方法？ |
| **数据关系** | 参数传入了什么？结果返回了什么？ |
| **状态关系** | 哪个对象内部的数据发生了变化？ |

这四种关系不能混为一谈。例如 `book.borrowOne()` 没有返回值，但它仍然有重要作用：改变 `Book` 的库存状态。

### 课堂练习 3：先预测，再调试（15 分钟）

在 IDEA 中对 `borrow()`、`ensureEligible()`、`borrowOne()` 设置断点。

1. 不运行程序，先画出你预计的调用顺序。
2. 用 **Step Into** 逐行进入方法，记录实际进入的类。
3. 在变量面板中观察 `Book.availableCopies` 如何变化。
4. 回到调用者，确认 `BorrowRecord` 如何被返回。
5. 如果调用的是接口方法，分别指出**变量声明类型**与**实际对象类型**。

**能预测调用链，再用调试器验证，比单纯“运行成功了”更能证明你理解代码。**

## 六、一次可以直接运行的小实验

将下面代码保存为 `BorrowDemo.java`。这不是生产级系统，而是专门用于理解**对象职责、方法调用、参数、返回值和状态变化**的最小实验。

```java
public class BorrowDemo {
    public static void main(String[] args) {
        User user = new User(1L, true);
        Book book = new Book(101L, 2);
        BorrowService service = new BorrowService();

        BorrowRecord record = service.borrow(user, book);
        System.out.println("借阅图书：" + record.getBookId());
        System.out.println("剩余库存：" + book.getAvailableCopies());
    }
}

class User {
    private final long id;
    private final boolean active;

    User(long id, boolean active) {
        this.id = id;
        this.active = active;
    }
    long getId() { return id; }

    void ensureEligible() {
        if (!active) {
            throw new IllegalStateException("USER_DISABLED");
        }
    }
}

class Book {
    private final long id;
    private int availableCopies;

    Book(long id, int availableCopies) {
        if (availableCopies < 0) {
            throw new IllegalArgumentException("NEGATIVE_STOCK");
        }
        this.id = id;
        this.availableCopies = availableCopies;
    }
    long getId() { return id; }
    int getAvailableCopies() { return availableCopies; }

    void borrowOne() {
        if (availableCopies == 0) {
            throw new IllegalStateException("NO_STOCK");
        }
        availableCopies--;
    }
}

class BorrowRecord {
    private final long userId;
    private final long bookId;

    BorrowRecord(long userId, long bookId) {
        this.userId = userId;
        this.bookId = bookId;
    }
    long getUserId() { return userId; }
    long getBookId() { return bookId; }
}

class BorrowService {
    BorrowRecord borrow(User user, Book book) {
        if (user == null || book == null) {
            throw new IllegalArgumentException("MISSING_ARGUMENT");
        }
        user.ensureEligible();
        book.borrowOne();
        return new BorrowRecord(user.getId(), book.getId());
    }
}
```

命令行执行：

```bash
javac BorrowDemo.java
java BorrowDemo
```

预期输出：

```text
借阅图书：101
剩余库存：1
```

**请注意**：这个版本没有数据库、没有借阅记录持久化，也没有处理多人并发借书。它的用途是把最基本的对象协作跑通。

### 改动代码并预测结果

- 把 `new User(1L, true)` 改为 `new User(1L, false)`。会发生什么？库存变化吗？
- 把 `new Book(101L, 2)` 改为 `new Book(101L, 0)`。会发生什么？
- 在 `borrow()` 中交换 `user.ensureEligible()` 与 `book.borrowOne()` 的顺序。用户无资格时，会出现什么新问题？

最后一个问题尤其重要：**相同的对象和方法，不同的协作顺序，可能导致不同的系统结果。**

## 七、协作不只是“调通”：失败后系统是否仍然正确？

现在把借书扩展为需要保存数据库的业务：

```java
user.ensureEligible();
book.borrowOne();
BorrowRecord record = new BorrowRecord(user.getId(), book.getId());
bookRepository.save(book);
recordRepository.save(record); // 假设这一行失败
```

这时不能只关心“抛出了什么异常”，还必须关心：

- `Book` 对象内存中的库存已经减少了吗？
- 数据库中的库存是否已经改变？
- 借阅记录是否存在？
- 用户是否会看到“借书失败”，但库存已经减少的矛盾结果？

真实工程需要结合**数据库事务、并发控制和失败恢复**处理这些问题。若数据库操作属于同一事务，可以通过事务回滚保证相应的数据库修改原子性；但这并不等于 Java 对象内存中所有字段都会被自动恢复，更不代表外部消息或远程接口调用也能随之回滚。

**一条完整的调用链，必须同时考虑成功路径和失败路径。**

## 八、需求变了，才真正看得出设计水平

已经能借书，不代表设计任务结束。现在逐步增加需求：

| 新需求 | 重点思考 |
|---|---|
| 教师最多借 20 本，学生最多借 5 本 | 规则需要哪些信息？放在 `User`、服务，还是独立策略里？ |
| VIP 可以预约无库存图书 | 是否出现了新的业务行为和状态？ |
| 借书成功后发送通知 | 通知对象应由谁调用？失败是否影响借书成功？ |
| 同一本书被两个人同时借走 | 如何防止库存超卖？单靠 `if` 够吗？ |
| 电子图书无需扣实体库存 | 现有设计在哪些地方需要修改？ |

每增加一条需求，都按顺序完成：

**说明变化 → 找到受影响的责任 → 修改方法契约与协作 → 编写测试 → 比较修改前后。**

不要一见到新需求就使用策略模式、状态模式或工厂模式。先确认原有代码究竟哪里难以修改，**让抽象解决实际存在的变化问题**。

请回答：

- 每个类是否承担了可独立说明的职责？

## 九、面对复杂代码，如何不再迷失？

接手陌生项目时，不建议从第一个文件开始挨个读完所有类。优先选一个真实业务入口，顺着调用链阅读：

```text
HTTP 请求
  → BorrowController.borrow()
  → BorrowService.borrow()
  → UserRepository.findById()
  → BookRepository.findById()
  → user.ensureEligible()
  → book.borrowOne()
  → BorrowRecordRepository.save()
  → 返回结果
```

注意：这只是**某种实现的典型调用顺序**，不是框架强制规定的流程。

对每次调用，固定问五个问题：

> **谁调用？调用谁？传什么？返回什么？改了什么状态？**

如果某一步失败，还要补第六问：

> **失败后，谁来处理，系统处于什么状态？**

这种方法既适用于自己设计程序，也适用于阅读开源项目、调试 Java 框架，以及审查 AI 生成的代码。

## 十、AI 已经会编程，为什么还要训练这些能力？

AI 能快速生成类、接口、方法和测试，但代码“看起来合理”并不等于业务正确。你仍然必须能够判断：

- AI 是否理解了真正的需求与业务边界？
- 为什么它把某个方法放在这个类中？
- 它引入的接口和类是否真的必要？
- 方法参数、返回类型、异常契约是否合理？
- 测试是否覆盖了关键失败路径？
- 需求变化后，哪些地方需要修改，修改有没有破坏其他行为？

课堂可以使用 AI，但建议遵守一个训练顺序：

**先自己画出流程和方法契约 → 再独立写出关键调用链 → 再让 AI 提供候选实现或重构建议 → 最后自己调试、验证、解释。**

## 离开课堂前，回答这 8 个问题

1. 面对一个新功能，为什么不应该第一步就创建很多类？
2. “一个类应该有一个职责”，这里的“职责”到底指什么？
3. `book.borrowOne()` 为什么可以没有参数和返回值？
4. 一个方法为什么返回 `Book`，另一个方法却返回 `void`？依据是什么？
5. 什么是对象关系、调用关系、数据关系、状态关系？
6. 对象协作时，为什么调用顺序可能影响正确性？
7. 增加一个类，究竟在什么条件下算改进，在什么条件下是过度设计？
8. AI 给出一套能运行的代码，你需要怎样验证它真的符合需求？

## 最后要记住的心智模型

**正向设计：**

```text
需求 → 业务行为 → 责任分配 → 对象与方法
     → 参数/返回值/异常契约 → 调用链 → 代码 → 测试
```

**反向理解：**

```text
代码 → 实际调用链 → 数据和状态变化
     → 对象职责 → 业务规则 → 原始需求
```

> **最重要的不是记住多少个设计模式，也不是写出多少个类，而是能面对一个真实问题，清楚地组织代码与对象，让系统正确协作，并且能够解释、验证和修改它。**
>
> 这才是从“会写代码”走向“会构造软件”的关键一步。
